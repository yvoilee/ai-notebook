# 10 · 可观测性、回放与评测

> 核验日期：2026-08-30  
> 主项目：OpenHands Software Agent SDK（Python）  
> 对照项目：OpenAI Codex（Rust）、LangGraph（Python）、PydanticAI（Python）

## 1. 一句话掌握

可观测性把 Agent 的每一步决策、工具调用、错误与成本变成结构化事件流；回放利用持久化状态从任意断点重跑；评测则把事件和产物转成可量化的回归门禁——三者共同决定一个 Agent 系统能否从 Demo 走向可运营。

## 2. 为什么需要它

Agent 系统和传统服务最大的不同是**失败不可直接归因**：一次任务失败可能是模型温度、prompt 漂移、工具超时、上下文截断、权限拒绝、沙箱环境差异或并发竞态中的任意一个，甚至多个叠加。只看最终输出等于黑盒。

朴素实现的问题：
- **只有文本日志**：日志是给人读的，无法按 step / tool / token / cost 聚合，也无法机器化回放。
- **没有结构化事件**：消息、工具调用、观察、错误混在一个对话数组里，想统计"工具重试率"或"平均每步时延"都要写 ad-hoc 解析。
- **无法重放单步**：模型输出有随机性，工具调用有副作用，想复现一次失败往往比修 bug 还难。
- **评测靠人工抽检**：没有回归集，每次改 prompt 或换模型都是赌博，能力回退发现得比用户还晚。

在 Agent / Harness / Runtime / Product 四层中，本范式主要落在 **Runtime 层**（事件、checkpoint、metrics、trace）并向上延伸到 **Harness 层**（评测、失败分类、回放契约）。Product 层的 UI 可视化和运营仪表盘建立在它之上。

### 核心概念区分

| 概念 | 作用 | 数据粒度 |
|---|---|---|
| **logs** | 人类可读的文本记录 | 自由文本 |
| **metrics** | 可聚合的数值指标（token、cost、latency、step count） | 数值 + 标签 |
| **traces** | 带因果关系的调用链（span + parent） | 结构化 span |
| **trajectory** | Agent 完整决策路径（action-observation 序列） | step 级别 |
| **causal replay** | 基于 checkpoint 从断点重跑，保留上游状态 | state + checkpoint |
| **deterministic assertion** | 不依赖模型判断的硬断言（文件是否存在、命令退出码） | 布尔 |
| **LLM judge** | 用模型评估输出质量（正确性、相关性、安全性） | 评分 + 理由 |
| **offline eval** | 在固定数据集上批量评测，用于回归 | 数据集驱动 |
| **online eval** | 生产环境实时或近实时评测，用于监控 | 生产流量 |
| **failure taxonomy** | 按失败阶段/原因的结构化分类（模型层 / 工具层 / 环境层 / 权限层） | 枚举 + 标签 |

## 3. 最小概念模型

一个可观测、可回放、可评测的 Agent 系统，核心是把"执行"和"记录"解耦：执行产生事件，事件写入 append-only 日志，日志既是观测入口也是回放输入。

```
            ┌─────────────┐
  user ────▶│  Agent Loop │──────▶ tool / env
            └──────┬──────┘
                   │ emits
                   ▼
            ┌─────────────┐
            │ Event Stream │  ◀── append-only, immutable
            └──────┬──────┘
                   │
         ┌─────────┼─────────┐
         ▼         ▼         ▼
     metrics    traces   artifacts
     (costs)    (spans)  (files, outputs)
         │         │         │
         └─────────┼─────────┘
                   │ feeds
                   ▼
            ┌─────────────┐
            │  Eval / Replay │
            └─────────────┘
```

关键对象：
- **TraceEvent**：带 id、timestamp、source、type、parent_id 的最小事件单元。
- **Checkpoint**：某一步的完整可恢复状态（消息、工具状态、环境快照指针）。
- **EvalCase**：输入 + 预期 + 评分函数的三元组。
- **FailureTaxonomy**：将失败映射到阶段/原因的分类树。

### 语言无关伪代码

```
# 可观测性 + 回放 + 评测的最小闭环伪代码

function run_agent_with_obs(task, tools, eval_fn):
    events = []                 # append-only event log
    checkpoints = []            # per-step state snapshots

    state = init_state(task)
    step = 0

    while not state.done and step < MAX_STEPS:
        # 1. 记录 checkpoint，支持从该步回放
        checkpoints.append(snapshot(state))

        # 2. 模型决策 → 产生 action event
        start = now()
        action = model_call(state.context)
        emit(events, TraceEvent(
            type="action", step=step,
            input_tokens=action.usage.input,
            output_tokens=action.usage.output,
            latency_ms=now() - start,
            parent_id=events[-1].id if events else None
        ))

        # 3. 工具执行 → 产生 observation event
        if action.tool_call:
            tool_start = now()
            try:
                result = tools[action.tool_name].execute(action.args)
                emit(events, TraceEvent(
                    type="observation", step=step,
                    tool=action.tool_name, status="success",
                    latency_ms=now() - tool_start
                ))
                state.apply_observation(result)
            except ToolError as e:
                emit(events, TraceEvent(
                    type="observation", step=step,
                    tool=action.tool_name, status="error",
                    error_type=e.category
                ))
                state.apply_error(e)
        else:
            state.done = True
        step += 1

    # 4. 评测：deterministic + LLM judge
    det_score = deterministic_assert(state, task)
    llm_score = eval_fn(state.final_answer, task, events)
    return RunResult(events, checkpoints, state, det_score, llm_score)

# 因果回放：从指定 checkpoint 重跑
function replay_from(checkpoint_id, checkpoints, new_tools=None):
    state = checkpoints[checkpoint_id].restore()
    return run_agent_from_state(state, new_tools or tools, start_step=checkpoint_id)
```

> 方法论说明：这是教学等价伪代码，不是任何项目的源码。真实实现中事件、checkpoint 和评测是解耦的子系统。

## 4. 关键设计决策

### 决策 1：事件模型——单一根类 vs 多层继承

OpenHands SDK 选择了**单一根类 Event + 两级继承**（`Event → LLMConvertibleEvent / InternalEvent → 具体事件类型`）。事件是 frozen Pydantic model，保证 append-only 不可变。

- **收益**：类型安全、可序列化、可 discriminated union 反序列化；事件流可以直接转 LLM 消息。
- **代价**：新增事件类型需要继承 + 注册，运行时扩展不灵活。
- **失败模式**：如果事件字段膨胀（每个子类型加特殊字段），序列化版本兼容会成为负担。

### 决策 2：回放粒度——消息级回放 vs checkpoint 级回放

- **消息级回放（Codex）**：保存所有历史消息，通过 `response_id` 标记分叉点，回放时重新组装上下文再跑。优点是实现简单；缺点是**无法恢复工具和环境状态**，重跑会产生新的副作用。
- **checkpoint 级回放（LangGraph）**：每步（super-step）保存完整 graph state，结合 checkpointer 可以从任意节点精确恢复。优点是可精确重放控制流；缺点是 checkpoint 体积大，且需要外部状态（数据库、文件系统）配合才能真正"完全回放"。

适用条件：纯对话 Agent 消息级足够；有状态副作用的 Agent（文件修改、API 调用）必须 checkpoint + 环境快照。

### 决策 3：评测方法——确定性断言 vs LLM Judge

- **确定性断言**：可重跑、零成本、无歧义，但只能覆盖"可机器判定"的属性（文件内容、退出码、JSON schema 校验）。
- **LLM Judge**：能评估语义质量、代码正确性、安全性等复杂属性，但自身有噪声（同一输出可能打分不同）、有成本、可能有偏差。

生产实践通常是**分层评测**：unit 层用确定性断言，integration 层用 LLM judge，production 层用人工抽检 + 线上指标。Pydantic Evals 的设计体现了这一点：内置 exact match / instance 等确定性 evaluator，同时支持 LLM-as-judge 和自定义 evaluator。

### 决策 4：trace 粒度——每模型调用 vs 每工具调用 vs 每 step

粒度越细，排查问题越容易，但数据量和成本也越高。常见做法：
- **每模型调用**必有 span（token、cost、latency、model name）。
- **每工具调用**必有 span（tool name、args 摘要、status、error）。
- **每 step** 聚合一次（step 号、action type、总时延、总 token）。

OpenHands 的事件系统天然覆盖了 action / observation 两级；LangGraph 则是 node 级 span + 内部 LLM/tool span 的树形结构。

### 决策 5：失败分类——自由标签 vs 固定分类法

自由标签灵活但不可比；固定分类法可比但容易漏类。推荐采用**两级分类**：
- 一级固定：`model_failure` / `tool_failure` / `env_failure` / `permission_failure` / `policy_failure` / `unknown`。
- 二级自由标签：如 `tool_failure → timeout`、`model_failure → format_error`。

FailureTaxonomy 的价值不在"一次分类对不对"，而在**长期趋势分析**——哪类失败在增长，哪类修复后下降了。

## 5. 代表项目代码佐证

### 5.1 OpenHands SDK：Event 基类与可观测入口

**项目**：OpenHands Software Agent SDK  
**语言**：Python  
**源码路径**：`openhands-sdk/openhands/sdk/event/base.py`  
**在执行链中的位置**：所有 agent 决策、工具执行、系统事件都通过 Event 子类发出，Conversation 持有 event log。

以下是教学等价代码，简化自源码，保留核心设计（immutable、LLM 可转换分层、token 统计）：

```python
# 教学等价实现，简化自 OpenHands SDK event/base.py
import uuid
from abc import ABC, abstractmethod
from datetime import datetime
from enum import Enum
from pydantic import BaseModel, ConfigDict, Field

class SourceType(str, Enum):
    USER = "user"
    AGENT = "agent"
    ENVIRONMENT = "environment"

class Event(BaseModel, ABC):
    """根类：不可变、带唯一 ID、带来源标记"""
    model_config = ConfigDict(extra="forbid", frozen=True)
    id: str = Field(default_factory=lambda: str(uuid.uuid4()))
    timestamp: str = Field(default_factory=lambda: datetime.now().isoformat())
    source: SourceType

class LLMConvertibleEvent(Event, ABC):
    """可转换为 LLM 消息的事件（参与模型上下文）"""
    @abstractmethod
    def to_llm_message(self) -> dict: ...

class ActionEvent(LLMConvertibleEvent):
    tool_name: str
    tool_args: dict
    thought: str = ""
    llm_response_id: str = ""
    input_tokens: int = 0
    output_tokens: int = 0

    def to_llm_message(self) -> dict:
        return {"role": "assistant", "content": self.thought,
                "tool_calls": [{"id": self.id, "type": "function",
                    "function": {"name": self.tool_name, "arguments": self.tool_args}}]}

class ObservationEvent(LLMConvertibleEvent):
    tool_call_id: str
    content: str
    status: str  # success / error
    error_type: str | None = None
    latency_ms: float = 0.0

    def to_llm_message(self) -> dict:
        return {"role": "tool", "tool_call_id": self.tool_call_id, "content": self.content}
```

> 源码事实：`Event` 使用 `frozen=True` 保证不可变、`extra="forbid"` 严格校验、`DiscriminatedUnionMixin` 支持多态序列化/反序列化。  
> 教学简化：移除了 Rich Text 可视化、多 tool call 合并逻辑、完整的事件类型体系。  
> 关键设计点：  
> 1. `source` 独立于 LLM role——来源归因和模型格式化是两个维度。  
> 2. `LLMConvertibleEvent` 是关键分层：不是所有事件都进模型上下文。  
> 3. `ActionEvent.llm_response_id` 是并行工具调用的分组键。

### 5.2 结构化 EvalCase 与可重放输入

以下 Python 代码展示如何构造结构化 `EvalCase`，并实现最简回放验证。这是教学代码，不是项目源码。

```python
# 教学等价：结构化 EvalCase 与失败分类
from dataclasses import dataclass, field
from typing import Callable

@dataclass
class EvalCase:
    """一个可重放的评测用例"""
    case_id: str
    task: str
    initial_state: dict           # 回放契约：定义"从什么状态开始算同一个用例"
    expected: dict                # 预期结果 / 约束
    failure_tags: list[str] = field(default_factory=list)

@dataclass
class EvalResult:
    case_id: str
    passed: bool
    score: float
    failure_category: str | None
    total_tokens: int
    total_cost: float

def run_eval(case: EvalCase, agent_fn: Callable,
             evaluators: list[Callable]) -> EvalResult:
    output = agent_fn(case.initial_state)   # 含 events / metrics
    score = 1.0
    failure = None
    for ev in evaluators:
        ok, reason = ev(output, case)
        if not ok:
            score = 0.0
            failure = reason
            break
    metrics = output.get("metrics", {})
    return EvalResult(
        case_id=case.case_id, passed=score > 0.5,
        score=score, failure_category=failure,
        total_tokens=metrics.get("total_tokens", 0),
        total_cost=metrics.get("total_cost", 0.0),
    )

# 不可确定性来源（eval 设计必须显式考虑）：
# 1. 模型 temperature > 0 → 输出不固定
# 2. 工具调用有副作用 → 重跑结果可能不同
# 3. 并行工具调用顺序不保证 → event 时序可能漂移
# 4. 时间/随机数相关工具 → 每次输出不同
# 5. 外部 API 限流/降级 → 可用性不稳定
```

> 方法论说明：`EvalCase.initial_state` 是回放契约的核心。如果初始状态不完整（缺文件系统快照、缺数据库状态），回放结果就不可比。

## 6. 热门项目横向对比

| 维度 | OpenHands SDK | OpenAI Codex | LangGraph | PydanticAI |
|---|---|---|---|---|
| **事件模型** | `Event` 根类 + 两级继承，frozen Pydantic，append-only | `EventMsg` enum（Rust），通过 EQ 队列流式推送，非穷尽枚举 | RunTree 模型（LangSmith），按 run 组织树结构，自动埋点 | OpenTelemetry-native，span 模型，Logfire 作为后端 |
| **Trace 粒度** | action / observation / message / internal event 四级 | 流式 delta + 完整 event，按 turn 组织 | graph / node / llm / tool 四层树形 span | span + attribute，可自定义到任意粒度 |
| **Replay 机制** | 基于 conversation event log 恢复，支持 fork | `response_id` 分叉 + `ThreadRollback`，消息级回放 | checkpoint-based time travel，每 super-step 保存状态 | 无内置 replay，依赖 OTel trace 做离线分析 |
| **Eval 支持** | 无内置 eval 框架，事件流可外接 | 无内置 eval 框架，rollout file 可用于审计 | 与 LangSmith eval 深度集成，支持 backtesting | 独立 `pydantic_evals` 包，代码优先，支持 LLM judge |
| **成本/Token 统计** | `LLM.metrics` + `conversation_stats`，内置 cost 配置 | 通过 tracing 导出（OTLP），需外部聚合 | LangSmith 内置 token/cost 统计 | Logfire 内置成本跟踪（genai-prices） |
| **隐私/数据边界** | 事件本地存储，server 可自托管 | rollout file 本地，traces 可选上送 | LangSmith 是云服务，数据出域 | Logfire 云服务，也可自托管 OTel 后端 |
| **失败分类** | 无内置 taxonomy，事件类型 + error 字段可推导 | 无内置 taxonomy，event error 变体区分 | LangSmith 支持自定义 tag/metadata 分类 | evaluator 返回结构化原因，可自定义分类 |

### 共同收敛的设计

1. **结构化事件是基础**：四个项目都没有用"纯文本日志"做可观测性入口，都有类型化的事件/span 模型。
2. **成本和 token 是一等指标**：都在 tracing 层面内置了 token/cost 统计，而不是事后从日志里扒。
3. **回放依赖状态持久化**：没有持久化状态就没有可靠回放。消息级回放只是"重跑一遍"，checkpoint 级回放才能精确复现。

### 仍有分歧的设计

1. **事件粒度设计哲学不同**：OpenHands 偏"领域事件"（每个语义事件一个类）；LangGraph 偏"通用 span"（用 run_type + metadata 区分）；Codex 是"协议事件"（面向前后端通信设计）。
2. **eval 是内置还是外置**：PydanticAI 把 eval 做成独立的代码优先框架；LangGraph 把 eval 绑定到 LangSmith 云服务；OpenHands 和 Codex 干脆不内置 eval。
3. **回放是否需要环境配合**：LangGraph 的 checkpoint 只保存 graph 内部状态；OpenHands 的 conversation replay 需要 workspace 配合才能恢复文件系统。都不"开箱即可完全回放"。

### 项目特有但不可盲目迁移的设计

- **OpenHands 的 `LLMConvertibleEvent` 分层**：因为它的事件流同时是模型上下文来源，所以需要这个区分。如果你的事件系统只做观测（不同时喂给模型），不需要这层。
- **Codex 的 rollout file**：面向 CLI session 的审计格式，适合本地 Coding Agent，不一定适合服务端 Agent。
- **LangGraph 的 time-travel + backtesting 组合**：依赖 LangSmith 云服务 + checkpointer 持久化，自托管需要自建这两层。
- **PydanticAI 的 span-based eval**：依赖 OpenTelemetry 生态，如果你的系统不用 OTel，这种 eval 方式接入成本高。

## 7. 方法论抽象

### 设计原则

1. **事件先行**：先定义事件模型，再写观测和评测代码。事件模型是所有下游系统的契约。
2. **append-only 不可变**：事件一旦写入就不能修改。需要纠正就写新事件，通过"补偿事件"处理。
3. **回放契约最小化**：每个 EvalCase 只保存必要的初始状态，避免冗余和不可比。
4. **分层评测**：确定性断言做底座，LLM judge 做语义层，人工抽检做质量锚点。
5. **失败分类驱动改进**：没有 failure taxonomy 就不知道该优化模型、工具还是环境。

### 决策顺序

```
定义事件模型 → 选 trace 粒度 → 实现 metrics 聚合 →
  决定 checkpoint 策略 → 设计回放契约 →
    建立 eval dataset → 实现 evaluator 分层 →
      建立 failure taxonomy → 接入回归门禁
```

### 可观察的不变量

- 事件 ID 全局唯一且单调递增（按时间戳排序时不能乱序）。
- 每个 `action` 事件必须对应一个 `observation` 事件（成功或失败），且 `tool_call_id` 匹配。
- 总 token = sum(input_tokens) + sum(output_tokens)，且等于模型侧统计。
- 从任意 checkpoint 回放，回放前 N 步的状态与原运行前 N 步状态一致（确定性前提下）。

### 从最小实现到生产实现的路径

1. **最小版**：在 agent loop 里加 `print` 式的结构化 JSON 日志，手算 token/cost。
2. **可用版**：引入事件基类 + 事件流订阅，接入 metrics 聚合（Prometheus / 自建），有 10–20 个 eval case 的回归集。
3. **生产版**：checkpoint 持久化 + 时间旅行回放、OTel trace 全链路、分层 eval（deterministic + LLM judge + 人工）、failure taxonomy 自动分类、回归门禁阻断合入。
4. **高级版**：生产 trace → 自动转 eval case 的闭环（类似 LangSmith backtesting）、失败自动聚类、A/B 评测平台。

## 8. 实践练习

### 练习：为一个极简 Agent 加可观测性和回放评测（30–60 分钟）

**目标**：给一个 ReAct 风格的 Python Agent 加上结构化事件、token/cost 统计、checkpoint 回放和一个确定性 evaluator。

**步骤**：

1. 写一个极简 Agent Loop（model call → tool call → observation → 循环），工具至少包含 `get_time` 和 `echo` 两个无副作用工具。
2. 定义 `TraceEvent` dataclass，字段至少含：id、timestamp、type（action/observation/error）、step、parent_id、extra（dict）。
3. 在 loop 的每个关键节点 emit 事件，action 事件记录 token 数和模型名，observation 事件记录工具名和时延。
4. 实现 `Metrics` 类：从事件流中聚合 total_tokens、total_cost、tool_call_count、error_count。
5. 实现 `checkpoint`：每步开始前保存当前 state（消息列表 + step 号），存到列表中。
6. 实现 `replay_from(step_idx)`：从指定 step 的 checkpoint 恢复，重新跑后续步骤，验证结果一致（因为工具是无副作用的 + temperature=0，应该完全一致）。
7. 写一个 `EvalCase` 和一个 `exact_match` evaluator，跑 3 个用例，输出通过率和平均成本。
8. 加一个 `failure_category` 字段，能区分 `model_format_error`、`tool_not_found`、`tool_execution_error`、`max_steps_exceeded` 四类。

### 9.2 生产落地检查清单

- [ ] 事件模型有版本号，支持向后兼容的反序列化
- [ ] token/cost 统计与模型提供方对账误差 < 1%
- [ ] 每个工具调用都有 span，含 status 和 error_type
- [ ] checkpoint 可从存储中恢复并通过一致性校验
- [ ] 至少有 30 个回归 eval case，其中确定性断言占比 > 50%
- [ ] failure taxonomy 覆盖 > 90% 的已知失败模式
- [ ] 评测结果作为 CI 门禁，回归不通过不能合入
- [ ] 生产事件 / trace 数据有脱敏策略，不泄露 secret 和 PII

### 9.3 常见误区

1. **"有日志就等于有可观测性"**：自由文本日志无法机器化聚合和回放。结构化事件是前提。
2. **"LLM judge 可以替代所有评测"**：LLM judge 自身有误差和成本，只能做语义层补充，不能替代确定性断言。
3. **"回放就是重新跑一遍"**：没有 checkpoint 和环境快照的重跑不是回放，只是"再执行一次"。如果有副作用，结果不可比。
4. **"eval case 越多越好"**：低质量或重复的 eval case 只会增加运行成本，不会提升置信度。case 需要多样性和代表性。
5. **"把所有事件都存下来"**：全量存储成本高且查询慢。应该分层：热数据存详细事件，冷数据存聚合指标和采样 trace。
6. **"失败分类要一次做对"**：taxonomy 是演进的，先有一个粗粒度版本跑起来，再根据数据迭代细化。

## 10. 边界与延伸阅读

### 不适用边界

- 本文讨论的是 Agent 系统的可观测性，不是通用 APM（Application Performance Monitoring）。通用 APM 关注服务间调用链，Agent 可观测性关注决策链。
- 回放不等于"可复现 bug"。如果 bug 出在环境层（网络、第三方 API、文件系统状态），只重放消息/状态是不够的，还需要环境快照。
- 评测不等于 benchmark。本文关注的是工程级回归门禁，不是学术 benchmark 的排行榜设计。
