# 11 · 领域观察—行动接口

> 核验日期：2026-08-30  
> 主项目：browser-use / Python  
> 对照项目：OpenAI Codex、Aider、Agent Zero

## 1. 一句话掌握

领域观察—行动接口（Domain Observation–Action Interface）是把一个具体环境（网页、代码库、桌面、数据库）的**状态表示**、**动作原语**、**失败模式**和**反馈闭环**抽象成 Harness 可组合的一等契约，让 Agent 在不感知环境细节的前提下完成 POMDP 式决策。

## 2. 为什么需要它

通用 Agent Harness 只定义了 tool schema 和 tool result，但不回答三个领域相关的问题：

1. **观察该长什么样？** 浏览器环境需要 DOM 树 + 截图 + Tab 列表；代码环境需要文件树 + repo map + 语法标签；桌面环境需要屏幕截图 + 窗口列表。如果 Harness 直接把原始环境数据塞给模型，每换一个领域就要重写 prompt 和错误处理。
2. **动作该如何校验与落地？** 一个 `click(index=5)` 是否有效，取决于当前页面上 index=5 是否仍然存在——这是环境状态决定的，不是 JSON Schema 能静态校验的。同理，代码编辑的 `apply_patch` 必须先检查上下文是否匹配。
3. **失败该如何分类？** 网页上的 `StaleElementError`、代码编辑的 `PatchFailedError`、桌面环境的 `WindowNotFoundError`，它们的重试策略完全不同——有的刷新页面即可，有的需要重新读取文件，有的需要人工介入。

朴素实现把这些统统塞进"tool 报错字符串"，模型只能靠自然语言猜测下一步，导致**错误恢复不稳定、重试不可控、评测难归因**。领域观察—行动接口的价值，就是把环境从"一组工具"升级为"一个带状态机的领域"。

它在四层架构中处于 Harness 与领域环境的边界：

```text
┌─────────────────────────────┐
│         Agent (policy)      │
├─────────────────────────────┤
│      Harness (loop/ctx)     │
├─────────────────────────────┤
│  Domain Observation-Action  │  ← 本范式
│  Interface (契约层)         │
├─────────────────────────────┤
│   Environment (browser/     │
│   codebase/desktop/...)     │
└─────────────────────────────┘
```

理论基础来自 **POMDP（Partially Observable Markov Decision Process，部分可观测马尔可夫决策过程）**：Agent 无法直接看到环境的真实状态 `s`，只能通过观察 `o ≈ O(s)` 推断，并通过动作 `a` 转移到新状态 `s' ~ T(s, a)`，接收奖励 `r = R(s, a)`。把这一框架落地到工程中，需要回答：

- **State representation**：环境状态用什么数据结构表示？哪些信息必须保留，哪些可以压缩？
- **Grounding**：模型输出的符号化动作（如 `click(5)`）如何"落地"到真实环境？符号与真实对象之间的绑定如何验证？
- **Action affordance**：在当前状态下，哪些动作是合法（afforded）的？如何把"能做什么"告诉模型？
- **Closed-loop correction**：动作执行后的反馈是否足够让 Agent 发现并修正错误？
- **Domain-specific failure**：哪些失败是领域特有的、需要结构化错误而非通用字符串？

## 3. 最小概念模型

领域观察—行动接口的核心是四个对象 + 一个闭环：

```
┌────────────┐  observe   ┌─────────────┐
│            │──────────▶│             │
│  Domain    │           │ Observation │
│ Environment│           │  (O(s))     │
│            │◀──────────│             │
└─────┬──────┘  execute  └──────┬──────┘
      │                         │
      │ transition              │ policy
      ▼                         ▼
┌────────────┐           ┌─────────────┐
│ Transition │◀──────────│   Action    │
│  (s', r)   │  feedback │   (a)       │
└────────────┘           └─────────────┘
```

四个核心对象：

| 对象 | 含义 | 关键属性 |
|---|---|---|
| **Observation** | Agent 看到的领域状态投影 | 时间戳、结构化状态、可选视觉/文本补充 |
| **Action** | Agent 能对环境做的原子操作 | 动作类型、目标引用、参数校验 |
| **Transition** | 动作执行后的状态变化反馈 | 新观察、成功/失败标志、副作用摘要 |
| **DomainError** | 领域特有的结构化错误 | 错误类型、可重试性、恢复建议 |

语言无关伪代码（教学等价，不是任何项目源码）：

```text
# 领域接口的最小契约
interface DomainInterface:
    def observe() -> Observation:
        """返回当前环境的结构化观察。"""

    def execute(action: Action) -> Transition:
        """执行动作，返回状态转移结果或领域错误。"""

    def affordances() -> list[ActionSchema]:
        """返回当前状态下可执行的动作模式。"""

# Agent 侧的闭环
def run_episode(domain, policy, max_steps):
    for step in range(max_steps):
        obs = domain.observe()
        if is_terminal(obs):
            return SUCCESS
        action = policy.decide(obs)
        transition = domain.execute(action)
        if isinstance(transition.error, DomainError):
            if transition.error.recoverable:
                policy.note_failure(transition.error)
                continue  # 重试或调整策略
            else:
                return FAILURE, transition.error
    return TIMEOUT
```

这个模型的关键在于：**Observation 和 DomainError 都是结构化的一等对象**，而不是字符串。Harness 可以基于结构化错误做重试策略、成本计算和错误分类评测，不必把所有失败都丢给模型用自然语言消化。

## 4. 关键设计决策

### 决策 1：观察表示的"结构化优先，视觉补充"原则

**选择**：优先输出结构化数据（DOM 元素列表、文件内容、语法标签），视觉/截图作为可选补充。

browser-use 的 `BrowserStateSummary` 以 `SerializedDOMState`（带 index 的交互元素列表）为主，screenshot 可选。Aider 的 repo map 是结构化的树形文本（文件 + 定义行），而非截图。

- 收益：token 效率高、可被工具/校验逻辑消费、可复现。
- 代价：对 canvas、WebGL、高度动态的 UI 不适用；需要持续维护结构化提取逻辑。
- 失败模式：结构化提取与视觉显示不一致时，模型产生 grounding 错误（点击了"看不见"的元素）。

### 决策 2：动作引用是索引还是稳定标识？

**选择**：用观察中分配的瞬时索引（index）引用目标，而非持久的 CSS selector / XPath / 绝对路径。

browser-use 的动作（`ClickElementAction`、`InputTextAction`）都通过 `index` 参数引用 `interactive_elements` 列表中的元素。每次观察重新生成 index。

- 收益：动作 schema 极简；模型不必记忆或生成 selector；减少注入风险。
- 代价：动作与观察强绑定——页面一变化 index 就失效，产生 stale element 问题。
- 失败模式：模型用过期 index 点击了错误元素。必须在执行时二次校验 index 对应的元素 hash 是否匹配。

> **源码事实**：browser-use 在 `dom/views.py` 中定义了 `MatchLevel` 枚举（EXACT、STABLE、XPATH、AX_NAME、ATTRIBUTE），用于在执行动作时校验元素是否仍匹配预期。这是 grounding 的关键防线。

### 决策 3：领域错误是结构化异常还是字符串？

**选择**：定义领域特有的异常类型，包含可重试标志、短记忆/长记忆摘要和上下文详情。

browser-use 的 `BrowserError` 有 `short_term_memory`、`long_term_memory`、`details` 三个层次的信息。`URLNotAllowedError` 是其子类。

- 收益：Harness 可以基于错误类型决定重试、降级或中止；模型收到的错误反馈是一致格式而非任意字符串。
- 代价：每个领域都要设计自己的错误分类；跨领域统一需要额外映射层。
- 失败模式：错误粒度过粗导致模型无法理解，或过细导致 Harness 维护成本爆炸。

### 决策 4：反馈延迟是同步还是异步？

**选择**：动作执行后是否等待环境稳定再返回新观察。

browser-use 的导航动作支持 `wait_until` 级别（commit / domcontentloaded / load / networkidle），等待页面稳定后再生成观察。Aider 的 edit 动作是同步的——文件写入立即完成。

- 收益：减少模型观察到中间状态的概率，避免无效 step 浪费。
- 代价：等待时间是预算消耗；"稳定"的判断在复杂环境（如持续动画、实时聊天）中不成立。
- 失败模式：等待策略与实际页面节奏不匹配，要么等太久要么等不够。

## 5. 代表项目代码佐证

### 主项目：browser-use（Python）

browser-use 是理解领域观察—行动接口的最佳样本：它把浏览器这个复杂环境封装成了清晰的 Observation → Action → Transition 闭环。

**源码路径参考**：
- 观察表示：`browser_use/browser/views.py`（`BrowserStateSummary`）、`browser_use/dom/views.py`（`SerializedDOMState`）
- 动作定义：`browser_use/tools/views.py`（各 Action Pydantic 模型）
- 会话与状态捕获：`browser_use/browser/session.py`（`BrowserSession.get_browser_state_summary`）
- 错误类型：`browser_use/browser/views.py`（`BrowserError`、`URLNotAllowedError`）

下面用教学等价代码展示核心闭环（**不是源码逐字复制**，是从多个文件提取的关键逻辑简化）：

```python
# 教学等价代码：browser-use 观察-动作闭环（含 grounding 与结构化错误）
from dataclasses import dataclass
from pydantic import BaseModel
from enum import Enum

@dataclass
class DOMElement:
    index: int; tag: str; text: str; stable_hash: str

@dataclass
class BrowserObservation:
    url: str; title: str
    interactive_elements: list[DOMElement]
    screenshot_b64: str | None = None
    error: str | None = None

class ClickAction(BaseModel):
    index: int   # 引用上一轮观察中的元素索引

class MatchLevel(str, Enum):
    EXACT = "exact"; STABLE = "stable"; XPATH = "xpath"

class BrowserDomainError(Exception):
    def __init__(self, kind, message, recoverable, short_term=None):
        self.kind = kind          # stale_element/navigation/auth/...
        self.recoverable = recoverable
        self.short_term = short_term   # 本轮反馈给模型的摘要
        super().__init__(message)

async def execute_click(session, obs: BrowserObservation,
                        action: ClickAction) -> BrowserObservation:
    # 1. index 范围校验
    if action.index >= len(obs.interactive_elements):
        raise BrowserDomainError(
            kind="stale_element",
            message=f"index {action.index} out of range",
            recoverable=True,
            short_term="Element no longer exists; re-observe.",
        )
    target = obs.interactive_elements[action.index]
    # 2. grounding：在当前真实 DOM 中按 stable_hash 重新匹配
    current_obs = await session.get_state(cached=False)
    match = find_element_by_hash(current_obs, target.stable_hash)
    if match is None:
        raise BrowserDomainError(
            kind="stale_element", message="Element disappeared",
            recoverable=True,
            short_term="Target not found on current page.",
        )
    # 3. 执行动作，捕获导航超时
    try:
        await session.click(target)
    except NavigationTimeout as e:
        raise BrowserDomainError(
            kind="navigation_timeout", message=str(e),
            recoverable=True,
            short_term="Page navigation timed out after 30s.",
        )
    # 4. 返回新观察（Transition 的观察部分）
    return await session.get_state()
```

这段教学代码体现了三个关键点：

1. **动作与观察的绑定**：`ClickAction.index` 引用的是上一次观察中的元素，执行时必须重新获取当前状态并校验。
2. **结构化错误**：`BrowserDomainError` 有 `kind`、`recoverable` 和分层记忆字段，Harness 可以据此决定重试或记入 memory。
3. **Grounding 分层匹配**：`MatchLevel` 从精确匹配到降级匹配，避免微小 DOM 变化导致所有动作失败。

> **不确定项**：browser-use 中"元素 hash 匹配"的具体调用链和默认匹配级别，因未能完整追踪 `service.py` 中的执行路径，以上为基于 `dom/views.py` 中 `MatchLevel` 定义和 `DOMInteractedElement` 结构的合理推断。

## 6. 热门项目横向对比

对比 browser-use、Codex、Aider、Agent Zero 四个项目在观察—行动接口上的设计取舍。它们分别代表浏览器、代码编辑器、代码 AI 配对编程、桌面操作系统四个不同领域。

| 维度 | browser-use（浏览器） | Codex（代码 CLI） | Aider（代码配对） | Agent Zero（桌面） |
|---|---|---|---|---|
| **观察表示** | DOM 元素列表（带 index）+ 可选截图 + Tab 列表 | 文件内容 + Shell 输出 + thread 消息 | repo map（PageRank 排名的定义树）+ 文件内容 + diff | 屏幕截图 + 终端输出 + 工具返回文本 |
| **动作空间** | 导航 / 点击 / 输入 / 滚动 / Tab 管理 / 提取 / 截图 | read_file / apply_patch / bash / mcp 工具 | edit-block / whole-file / search-replace / udiff 多种编辑格式 | 浏览器 / 终端 / 文件系统 / 子 Agent / 视觉 |
| **动作引用方式** | 元素 index（瞬时，每轮重新生成） | 文件路径 + 行号 / patch 上下文 | 文件路径 + 编辑标记 / 搜索字符串 | 坐标 / 窗口句柄 / 命令字符串 |
| **Grounding 校验** | stable_hash + MatchLevel 降级匹配 | 文件内容哈希 / patch 上下文匹配 | 编辑块 fence 匹配 + lint 回环 | 视觉确认（不确定）|
| **领域错误类型** | `BrowserError`（含 short/long term memory）、`URLNotAllowedError` | 工具执行错误 + sandbox 拒绝 + patch 应用失败 | 编辑格式错误 + lint/test 失败 | 工具未找到 + 执行异常（偏通用） |
| **认证/持久状态** | 浏览器 profile（cookie/localStorage）、`profile-use` 工具 | 继承宿主管线 / 环境变量 / git 配置 | .env + git config + 项目本地配置 | 桌面 session（X11/cookie）+ 用户配置 |
| **失败恢复** | 自动重连（指数退避，3 次）、状态捕获超时返回空状态 | 审批 / 重试 / sandbox 降级 | lint 修复循环（模型自修复编辑） | 依赖模型自然语言推理 |
| **状态持久化** | 浏览器 profile 目录 + storage state | thread store（JSONL + SQLite） | 对话历史 + git 提交历史 | agent data dict + history |
| **反馈延迟** | 可配置 wait_until（domcontentloaded/load/networkidle） | 同步（文件操作）+ 异步等待（shell 命令） | 同步（文件写入）+ 子进程等待（lint/test） | 取决于具体工具（浏览器/终端异步） |

### 共同收敛的设计

1. **观察结构化优先**：四个项目都优先把环境状态编码为结构化文本（DOM 列表、repo map、文件内容），而非纯视觉。视觉是补充通道。
2. **动作原子化**：都选择细粒度原子操作（click、type、read_file、apply_patch）而非大颗粒"完成任务 X"动作。原子动作让闭环更短、错误更可归因。
3. **错误即反馈**：都把领域错误作为新一轮观察的一部分喂回模型，形成 closed-loop correction。

### 仍有分歧的设计

1. **引用机制**：browser-use 用瞬时 index，Codex/Aider 用文件路径 + 上下文，Agent Zero 用坐标/命令。哪种最可靠取决于领域——网页是高频变化的 DOM，代码是相对稳定的文件系统，桌面是不可预测的 GUI。
2. **错误结构化程度**：browser-use 定义了分层记忆的 `BrowserError`，Codex 有 protocol-level 错误但偏系统级，Aider 更多依赖 lint 输出的自然语言，Agent Zero 错误结构最弱。
3. **认证持久化**：浏览器用 profile（完整 cookie/storage），代码环境用 git/.env/ssh key，桌面用完整 X session。粒度差异很大。

### 项目特有但不可盲目迁移的设计

- **browser-use 的 index + stable_hash 双层引用**：只适合 DOM 这类"每轮可完整重建元素列表"的环境。对文件系统无意义。
- **Aider 的 lint 修复循环**：本质是利用编译器/静态分析器做领域 oracle。只有有成熟编译器/类型系统的领域（代码、SQL、配置文件）才能复制。
- **Agent Zero 的完整桌面 session**：观察空间最大（屏幕像素 + 全部进程），但 grounding 最困难，错误恢复最不可控。适合作为能力上限样本，不适合作为通用范式直接推广。

## 7. 方法论抽象

### 设计原则

1. **Observation 是契约，不是 raw data**：不要把浏览器的完整 DOM 树或代码库的全部文件直接扔给模型。定义 Observation 数据类，明确哪些信息保留、哪些压缩、哪些丢弃。
2. **Action 的目标引用必须可校验**：任何动作如果引用了环境中的对象（元素、文件、窗口、行号），执行前必须在当前状态下重新验证该对象是否存在且匹配预期。这是 grounding 的工程落地。
3. **DomainError 要有可重试语义**：不是所有错误都该立刻中止，也不是所有错误都该盲目重试。`recoverable` 标志 + 错误分类是 Harness 做策略决策的基础。
4. **观察—动作—反馈的闭环要短**：原子动作优于复合动作。闭环越短，错误定位越精确，模型的推理负担越小。

### 决策顺序

设计一个新的领域接口时，按以下顺序决策：

```
1. 定义 Observation：Agent "看到"什么？
   → 结构化主通道 + 可选补充通道（视觉/音频）
   → token 预算内的信息优先级

2. 定义 Action Space：Agent "能做什么"？
   → 原子动作还是组合动作？
   → 目标如何引用（索引/路径/坐标/ID）？

3. 定义 Grounding 校验：动作执行前如何验证目标存在？
   → 精确匹配 / 模糊匹配 / 多级降级匹配？

4. 定义 DomainError：常见失败模式有哪些？
   → 哪些可重试？哪些需要人工介入？
   → 错误反馈中该包含多少上下文？

5. 定义 State Persistence：哪些环境状态跨步骤保留？
   → 认证态 / 会话态 / 缓存态
   → 如何导出和恢复？

6. 定义 Termination：如何判断任务完成或失败？
   → 成功判据（结构化输出 / 人工确认）
   → 失败判据（步数/时间/特定错误类型达到阈值）
```

### 可复用接口骨架（方法论推断）

抽象层面，任何领域接口都可以用以下泛型形态来描述（不是特定语言实现，是接口形态规范）：

- `observe() -> Obs`：获取当前结构化观察。
- `execute(action: Act) -> Obs`：执行动作并返回新观察；失败时抛出结构化 `DomainError`。
- `close()`：释放领域资源（浏览器会话、文件句柄、桌面连接等）。
- `DomainError.kind`：错误分类标签。
- `DomainError.recoverable`：是否可自动重试。
- `DomainError.short_term`：本轮反馈给模型的简短摘要。
- `DomainError.long_term`（可选）：写入长期记忆的经验摘要。

Harness 侧不需要知道 Obs 和 Act 的具体类型，只需要知道它们是结构化对象，并且 execute 可能抛出特定类型的 DomainError。这就是为什么领域接口应该是 Generic Protocol——形态统一，类型因领域而异。

### 从最小实现到生产实现的路径

1. **最小实现**：Observation = 环境原始输出（原始 DOM、原始文件），Action = 单个工具函数，错误 = 字符串异常。能跑通闭环，但不可靠。
2. **结构化升级**：定义 Observation 数据类，提取关键信息（交互元素、repo map）；定义 Action schema，做参数校验。
3. **Grounding 加固**：动作执行前校验目标存在性；引入稳定标识（hash、路径校验、上下文匹配）。
4. **错误分类**：梳理领域失败模式，定义结构化 DomainError 层次；为每种错误关联默认重试策略。
5. **生产级**：加入认证态管理、状态快照/恢复、观测性（trajectory、错误分类统计）、评测集（领域特定的成功/失败用例）。

## 8. 实践练习

### 30–60 分钟练习：实现一个极简浏览器领域接口

**目标**：用 Playwright 封装一个符合 Observation–Action 契约的浏览器领域，包含 3 种动作和 2 种结构化领域错误。

**步骤**：

1. **定义数据结构**（10 分钟）：
   - `BrowserObservation`：包含 `url`、`title`、`interactive_elements`（list of dict: `{index, tag, text}`）
   - `ClickAction(index: int)`、`NavigateAction(url: str)`、`ExtractAction(selector: str)`
   - `StaleElementError`（recoverable=True）、`NavigationTimeoutError`（recoverable=True）

2. **实现 observe()**（10 分钟）：
   - 用 Playwright `page.$$('button, a, input, select')` 获取交互元素
   - 分配 index，提取 tag 和 textContent，组装成 `BrowserObservation`

3. **实现 execute()**（15 分钟）：
   - Navigate：`page.goto(url, timeout=15000)`，超时抛 `NavigationTimeoutError`
   - Click：先校验 index 是否在 `interactive_elements` 范围内，再用 `nth()` 点击；若元素 detached，抛 `StaleElementError`
   - Extract：用 `page.query_selector_all(selector)` 提取文本

4. **跑通闭环**（10 分钟）：
   - 写一个手动策略函数，依次执行 Navigate → Observe → Click → Observe
   - 故意触发一次 StaleElement（导航后用旧 index），验证错误被正确捕获并结构化返回

5. **进阶挑战**（可选，+15 分钟）：
   - 为 Click 加入 stable_hash 校验：在 observe 时为每个元素计算 hash（tag + text + aria-label），execute 时重新计算并比对

**检验标准**：
- observe() 返回结构化对象（不是 raw HTML）
- execute() 对无效 index 抛出结构化 `StaleElementError`（不是通用 Exception）
- 闭环可执行至少 3 轮（navigate → observe → click → observe → extract → observe）

## 9. 掌握检查

### 自测问题

1. **为什么 browser-use 用 index 引用元素而不是 CSS selector？这种设计的主要风险是什么？如何缓解？**

2. **在 POMDP 框架中，grounding 对应的是哪一步？为什么通用 tool schema 不能解决 grounding 问题？**

3. **DomainError 和普通 Exception 的区别是什么？为什么需要 `short_term_memory` / `long_term_memory` 这样的分层信息？**

4. **Aider 的 lint 修复循环是一种什么样的 closed-loop correction？它依赖的领域 oracle 是什么？为什么这种模式在浏览器领域难以复制？**

5. **如果你要为一个"数据库查询 Agent"设计观察—行动接口，Observation、Action、DomainError 分别应该包含什么？**

### 生产落地检查清单

- [ ] Observation 是否有明确的 token 预算和信息优先级？
- [ ] Action 的目标引用是否在执行前经过 grounding 校验？
- [ ] 领域常见失败模式是否都有对应的结构化 `DomainError` 子类？
- [ ] 每种 DomainError 是否标注了 `recoverable` 和默认重试策略？
- [ ] 认证态 / 会话态是否有独立的导出/恢复机制？
- [ ] 观察—动作闭环是否有超时和 step budget 保护？
- [ ] 是否有领域特定的评测集，可以量化错误恢复成功率？
- [ ] 领域接口是否可以被 mock，用于离线测试 Agent 策略？

### 常见误区

1. **"观察越全越好"**：把完整 HTML、全量文件系统都塞给模型。实际上 token 有限，信息噪声会淹没关键信号，还会拖慢每轮速度。
2. **"动作粒度越大越高效"**：设计"完成整个任务"的大动作。实际上粒度越大，失败越难归因，重试成本越高，模型越难从错误中学习。
3. **"错误字符串足够了"**：用自然语言字符串描述所有错误。模型可以理解，但 Harness 无法基于错误类型做策略决策，也无法做错误分类统计和回归评测。
4. **"grounding = 参数校验"**：以为 JSON Schema 校验参数就是 grounding。真正的 grounding 是校验"动作引用的对象在当前环境状态下仍然存在且语义一致"——这是运行时检查，不是静态 schema 检查。
5. **"一个接口通吃所有领域"**：试图用统一的 Observation/Action 抽象覆盖浏览器、代码、桌面、数据库。领域差异太大，强行统一会变成最低公分母，失去每个领域的结构化优势。正确做法是统一接口形态（Protocol），但每个领域有自己的 Observation/Action/DomainError 具体类型。

## 10. 边界与延伸阅读

### 适用边界

领域观察—行动接口适用于 Agent 需要与**有状态、可观察、可交互**的外部环境反复交互的场景：

- 浏览器自动化、RPA、网页测试
- 代码编辑、代码审查、重构
- 桌面 / 移动 GUI 自动化
- 数据库操作、API 编排、云资源管理
- 机器人、物联网设备控制

不适用于：

- 纯推理任务（不需要与外部环境交互）
- 单轮工具调用（不需要闭环反馈）
- 环境状态完全不可观测（没有观察信号就无法构建 Observation 契约）
