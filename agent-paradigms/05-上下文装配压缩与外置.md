# 05 · 上下文装配、压缩与外置

> 核验日期：2026-08-30  
> 主项目：Letta Code（TypeScript）  
> 对照项目：Pi、Codex、DeerFlow、OpenClaw

---

## 1. 一句话掌握

**Context window 是编译产物，不是数据库。** Agent Harness 需要把分散的 system 指令、项目说明、历史消息、工具输出和外置记忆，按优先级和 token budget 动态组装（compile）成模型实际看到的上下文；当窗口逼近上限时，通过压缩（compaction）把旧内容外置为可恢复的 artifact，而不是简单丢弃。

---

## 2. 为什么需要它

### 问题从何而来

一个长任务 Agent 会在运行中持续累积信息：用户指令、工具返回、文件内容、中间思考、错误重试……朴素实现把所有消息原样塞回窗口，最终必然撞上上下文长度上限。更隐蔽的问题是：

- **消息列表 ≠ 有效上下文**。大部分历史消息对下一步决策没有帮助，却消耗了 token。
- **直接截断会丢失恢复线索**。如果只保留最新 N 条消息，Agent 会忘记"我为什么在做这件事"，任务目标和中间约定全部丢失。
- **长上下文不等于长期记忆**。窗口再大也有边界，跨会话、跨任务的信息必须外置存储。

### 朴素实现为何失败

把 `messages[]` 直接 append 到模型调用是最朴素的做法，但它有三个结构性缺陷：

1. **没有分层**。system 指令、项目背景、历史消息、工具输出权重不同，不能用"时间远近"一刀切。
2. **没有预算感知**。等窗口爆了才处理，往往已经来不及——工具返回可能一次就吃掉一半窗口。
3. **没有外置结构**。被挤出去的信息变成黑洞，既不能检索，也不能在需要时重新拉回。

### 它在 Harness 中的位置

上下文装配处于 Harness 层的核心位置，介于"历史/记忆存储"和"模型调用"之间：

```text
┌──────────────┐  compile  ┌─────────────────┐  call  ┌────────┐
│ Source of    │──────────▶│ ContextCompiler │───────▶│ Model  │
│ Truth        │           │ (按优先级 + budget) │        └────────┘
│ - system     │           └─────────────────┘
│ - project    │                    ▲
│ - history    │                    │ compact
│ - tool results│                   ▼
│ - memory     │           ┌─────────────────┐
└──────────────┘           │ Externalized    │
                           │ Artifacts       │
                           │ (summary, recall│
                           │  pointers, …)  │
                           └─────────────────┘
```

它向上承托决策质量，向下决定 token 成本和任务长度上限。

## 3. 最小概念模型

### 核心对象

| 概念 | 定义 |
|---|---|
| **Source of Truth** | 原始、完整、不可篡改的信息源。包括系统指令、项目配置、完整消息历史、外置记忆文件。 |
| **Working Set** | 当前轮次模型实际能看到的信息集合。是 Source of Truth 的一个投影。 |
| **ContextCompiler** | 把 Source of Truth 中的不同来源按优先级和 token 预算编译成 working set 的组件。 |
| **CompactionPolicy** | 定义何时触发压缩、压缩哪些内容、压缩后保留什么指针的策略。 |
| **ContextArtifact** | 压缩后产生的外置产物——摘要、索引、指针、被替换的原始消息 ID 范围。 |
| **Recall** | 从外置 artifact 或长期记忆中检索信息并重新注入 working set 的动作。 |

### 数据流

```text
Source of Truth (持久化)
  ├── system prompt (最高优先级，始终保留)
  ├── project instructions (高优先级)
  ├── memory blocks / MemFS (按投影规则装配)
  ├── tool schemas (必须)
  └── message history (可变，是压缩主要对象)
        │
        ▼  ContextCompiler.compile(budget)
        │
  Working Set (本轮 context window)
        │
        ▼  model 调用 → 新消息追加
        │
  预算检查 → 超过阈值 → CompactionPolicy.trigger()
        │
        ▼
  生成 ContextArtifact (summary + pointers)
  用 artifact 替换历史消息的前半段
  保留恢复线索（原始消息 ID 范围）
```

### 语言无关伪代码

```python
class ContextCompiler:
    def __init__(self, budget, sources):
        self.budget = budget          # token 上限
        self.sources = sources        # 各来源 + 优先级

    def compile(self, new_items=None):
        """按优先级装配，返回 working set"""
        result = []
        remaining = self.budget

        # 高优先级：system、project、tool schema —— 必须放入
        for src in self.sources.high_priority():
            tokens = estimate(src.content)
            if tokens > remaining:
                raise ContextOverflowError(
                    "mandatory content exceeds budget")
            result.append(src)
            remaining -= tokens

        # 中优先级：记忆块 / MemFS 投影
        for mem in self.sources.memory_projection():
            tokens = estimate(mem.content)
            if tokens <= remaining:
                result.append(mem)
                remaining -= tokens

        # 低优先级：历史消息 —— 从新到旧遍历，插入头部保持时序
        for msg in reversed(self.sources.history):
            tokens = estimate(msg)
            if tokens <= remaining:
                result.insert(0, msg)  # 最新在前，最终按时间正序
                remaining -= tokens
            else:
                break

        if new_items:
            result.extend(new_items)

        return result, remaining

    def maybe_compact(self, used_tokens):
        """接近上限时触发压缩，返回 artifact"""
        if used_tokens < self.budget * 0.85:
            return None  # 不触发

        old_range = self.sources.history.oldest_portion(0.4)
        summary = run_compaction_model(old_range)
        artifact = ContextArtifact(
            summary=summary,
            replaces_message_ids=[m.id for m in old_range],
            created_at=now()
        )
        # 用 artifact 替换历史中的旧消息
        self.sources.history.replace_range(old_range, artifact)
        return artifact
```

## 4. 关键设计决策

### 决策 1：Context 是编译产物，还是原始历史的切片？

- **编译产物派**（Letta Code、DeerFlow）：把 system、项目指令、记忆文件、历史消息等多种来源按规则动态组装，每轮可能不同。
  - 收益：灵活，记忆可以被编辑、投影、重新组织；Agent 可以改写自己的"人格"和知识。
  - 代价：实现复杂，需要处理编译顺序、依赖、冲突；每次编译都有成本。
  - 失败模式：编译规则出错可能导致关键信息静默丢失，难以调试。
- **历史切片派**（Codex、Pi）：消息历史是线性的，context 就是历史的一个连续区间加上固定的 system 前缀。
  - 收益：简单，可预测，容易做 diff 和回放。
  - 代价：记忆和项目信息必须以消息形式注入，修改历史等于篡改轨迹。
  - 失败模式：长任务中早期关键指令被挤出窗口，任务漂移。

**适用条件**：短期、任务型 Agent 用历史切片足够；长期、有身份和成长属性的 Agent 需要编译式架构。

### 决策 2：压缩的粒度——整段摘要 vs 逐条淘汰

- **整段摘要**（Codex Memento、Letta compaction）：把历史的前半段交给模型生成一段摘要，用摘要替换原始消息。
  - 收益：语义保留好，摘要本身就是可读的 artifact。
  - 代价：需要额外一次模型调用；摘要本身可能丢失细节；多次压缩后误差累积。
- **逐条淘汰**（简单 truncation）：从最旧的消息开始丢弃，直到空间足够。
  - 收益：零成本，确定性强。
  - 代价：丢失语义，可能丢掉任务目标。
  - 失败模式：Agent 忘记"我在干嘛"，进入无效循环。

**实践中的混合策略**：工具输出优先 truncation（因为可重放），对话历史优先 summarization。

### 决策 3：外置介质——文件系统 vs 数据库 vs 向量库

- **文件系统 / Git**（Letta Code MemFS）：记忆以 Markdown 文件形式存在 git 仓库中，版本化、可审计、可 diff。
  - 收益：人类可读，可直接编辑，天然带版本历史；Agent 可以用熟悉的文件操作管理记忆。
  - 代价：检索靠 grep 和目录结构，不适合大规模语义搜索。
- **数据库 / Checkpoint**（Codex session、DeerFlow LangGraph checkpointer）：历史消息和状态存在 SQLite/Postgres。
  - 收益：查询高效，支持按 ID 精确恢复。
  - 代价：内容偏原始消息结构，不是面向"记忆"的组织。
- **向量库**（常见于 RAG 系统）：把记忆做 embedding，用语义相似度检索。
  - 收益：召回能力强，适合大规模知识库。
  - 代价：黑盒，难以审计；embedding 成本；难以精确编辑。

**核心权衡**：可审计性 vs 检索能力。MemFS 的设计选择是"Agent 自己能管理的记忆"，优先可编辑、可版本控制。

### 决策 4：压缩触发条件——阈值触发 vs 按需触发 vs 周期触发

- **阈值触发**（Codex auto-compact）：当 token 用量达到预算的某个比例（如 85%）时自动触发。
  - 收益：全自动，用户无感知。
  - 代价：可能在任务中间打断；阈值不当可能导致反复压缩。
- **按需触发**（用户手动 `/compact`）：用户决定何时压缩。
  - 收益：可控，避免关键时刻打断。
  - 代价：依赖用户判断，长任务中可能忘记。
- **周期触发**（Letta reflection/dreaming）：按 step 数或时间周期进行反思和记忆整理。
  - 收益：不仅压缩空间，还整合知识、提炼规律。
  - 代价：计算成本高；适合长期运行的 Agent，不适合短任务。

## 5. 代表项目代码佐证

### Letta Code：MemFS 与上下文编译

Letta Code 的核心设计是"memory-first agent"——Agent 的身份、知识和技能都以 Markdown 文件形式存在一个 git-backed 的内存文件系统（MemFS）中。上下文不是消息列表，而是从 MemFS 投影（project）到窗口内的编译产物。

**源码路径**：`src/agent/memory-filesystem.ts`、`src/agent/memory-format.ts`、`src/agent/memory.ts`、`src/tools/impl/memory.ts`  
**说明**：以下是教学等价代码，不是源码逐字复制，用于展示 MemFS 的核心工作流。

```typescript
// 教学等价实现：MemFS + 上下文编译（对应 Letta Code 多个模块）

interface MemoryBlock {
  label: string;          // 如 "persona", "human", "skills/research"
  content: string;
  readOnly: boolean;
  filePath: string;       // MemFS 中的相对路径
}

interface MemFS {
  blocks: Map<string, MemoryBlock>;
  format: "memfs-v1" | "memfs-v2";
}

class ContextCompiler {
  private memfs: MemFS;
  private tokenBudget: number;

  constructor(memfs: MemFS, tokenBudget: number) {
    this.memfs = memfs;
    this.tokenBudget = tokenBudget;
  }

  // 从 MemFS 按优先级投影出 system 上下文
  compileSystemContext(priorityLabels: string[]): string {
    let result = "";
    let remaining = this.tokenBudget * 0.4; // system 占 40%

    for (const label of priorityLabels) {
      const block = this.memfs.blocks.get(label);
      if (!block) continue;
      const estimated = estimateTokens(block.content);
      if (estimated <= remaining) {
        result += `\n## Memory: ${label}\n${block.content}\n`;
        remaining -= estimated;
      }
    }
    return result.trim();
  }

  // Agent 修改记忆 → git commit → 下次编译生效；只读块受保护（错误路径）
  async updateMemory(label: string, newContent: string): Promise<void> {
    const block = this.memfs.blocks.get(label);
    if (!block || block.readOnly) {
      throw new Error(`Cannot modify ${label}: not found or read-only`);
    }
    block.content = newContent;
    await writeFile(block.filePath, newContent);
    await gitCommit(block.filePath, `memory: update ${label}`);
  }
}
```

**关键点解读**：

1. **MemFS 是 source of truth，context 是投影**。Agent 修改记忆文件 → git commit → 下一轮 context 编译时自动生效。这和"消息历史即上下文"的模型有本质区别。
2. **格式版本化（memfs-v1 / v2）**：v2 要求每个目录有 `MEMORY.md` 索引文件，只有被索引的内容才会投影到上下文。这给了 Agent 自己组织结构的能力。
3. **读/写分离**：`persona` 等核心块标记为 `read_only`，Agent 不能改写自己的基本设定；但其他块可以自由创建、编辑、删除。
4. **Git 作为天然审计层**：每次记忆变更都有 commit，作者是 Agent ID，可追溯、可回滚。

### Codex：Memento 压缩策略

Codex 采用线性消息历史 + Memento 压缩策略。当上下文接近上限时，自动调用模型生成摘要，用摘要替换旧消息。

**源码路径**：`codex-rs/core/src/compact.rs`、`codex-rs/core/src/context_manager/history.rs`  
**说明**：Codex 原生为 Rust，以下为 TypeScript 教学重写，仅展示压缩触发与 artifact 替换的核心逻辑。压缩选择算法（最早 40%，最少 3 条）和失败路径（摘要超窗口时逐条丢弃旧消息后重试）在代码外以文字说明，不在代码中展开。

```typescript
// Codex（Rust 原生，TypeScript 教学重写）：Memento 压缩核心逻辑
// 对应 codex-rs/core/src/compact.rs

const SUMMARY_PREFIX = "=== CONTEXT SUMMARY ===";

interface CompactionArtifact {
  summary: string;
  replacedMessageIds: string[];
  windowNumber: number;
}

class CompactManager {
  private history: { id: string; role: string; content: string }[] = [];
  private budget: number;
  private windowCount = 0;

  constructor(budget: number) { this.budget = budget; }

  // 阈值触发：达到 85% 时替换最早 40% 为摘要；返回 artifact 或 null
  async maybeAutoCompact(usedTokens: number):
      Promise<CompactionArtifact | null> {
    if (usedTokens < this.budget * 0.85) return null;
    const cutIdx = Math.floor(this.history.length * 0.4);
    if (cutIdx < 3) return null;
    const oldItems = this.history.slice(0, cutIdx);
    // 失败路径（代码中未展开）：超窗口则逐条丢弃后重试
    const summary = await callModelForSummary(oldItems);
    this.windowCount++;
    const artifact: CompactionArtifact = {
      summary: `${SUMMARY_PREFIX}\n${summary}`,
      replacedMessageIds: oldItems.map(m => m.id),
      windowNumber: this.windowCount,
    };
    // 用摘要替换旧消息；SUMMARY_PREFIX + windowNumber 作为恢复指针
    this.history = [
      { id: `summary-${this.windowCount}`, role: "user",
        content: artifact.summary },
      ...this.history.slice(cutIdx),
    ];
    return artifact;
  }
}
```

**关键点解读**：

1. **阈值触发 + 增量替换**：不是等窗口爆了才处理，而是达到 85% 就提前压缩，每次替换约 40% 的旧内容。
2. **摘要作为恢复指针**：压缩后的历史中，摘要消息带 `SUMMARY_PREFIX` 特殊标记，系统可识别它是 artifact 而非真实用户消息。
3. **压缩自身的失败路径**：生成摘要的模型调用也可能超窗口——Codex 的处理方式是继续丢旧消息直到能装下，保证压缩过程本身不会卡死（此逻辑未在上方精简代码中展开）。
4. **多次压缩的累积误差**：Codex 会在多次压缩后发出警告，因为每一轮摘要都会丢失细节，长期累积可能导致任务漂移。

### 共同收敛的设计

1. **System 指令永远最高优先级**：所有项目都把 system/project instructions 放在不可压缩区。
2. **压缩是有损的**：没有项目声称无损压缩——都承认压缩会丢失细节，只是程度和策略不同。
3. **工具输出优先截断**：相比对话历史，工具返回值更容易被 truncate，因为工具可以重跑。

### 仍有分歧的设计

1. **编译式 vs 切片式**：Letta 和 DeerFlow 走编译路线，Codex 和 Pi 走线性切片路线。这背后是"Agent 是否有独立于对话的身份"的设计哲学差异。
2. **压缩是否需要模型参与**：Codex 用 LLM 生成摘要（成本高、语义好），简单系统用 truncation（零成本、语义差）。
3. **记忆与历史是否分离**：Letta 严格区分记忆（MemFS）和历史（消息），Codex 则把记忆信息也编码进消息历史。

### 项目特有但不可盲目迁移的设计

- Letta 的 **MemFS + Git**：适合长期、有身份的 Agent，但对短期任务型 Agent 是过度设计。
- Codex 的 **远程压缩 API**（`/responses/compact`）：依赖特定模型供应商，不通用；但加密压缩内容的思路值得关注。
- DeerFlow 的 **渐进技能加载**：只在需要时加载 skill 到上下文，适合技能多但单任务用得少的场景。

## 7. 方法论抽象

### 设计原则

1. **Context 是资源，不是存储**。像管理内存一样管理 context window——有分配、有回收、有淘汰策略。
2. **优先级分层，不搞一刀切**。system > project > memory > recent history > old history > tool output，每层有不同的保留策略。
3. **压缩要有恢复指针**。被移走的内容不能消失，必须留下"这里有东西被压缩了"的标记和找回路径。
4. **Source of Truth 与 Working Set 分离**。窗口里的是 working set，背后要有完整的 source of truth 可以重建。
5. **压缩本身也是成本**。一次 LLM 压缩 = 一次模型调用 = 时间 + 费用；要权衡"压缩省的 token"和"压缩花的 token"。

### 决策顺序

从零构建 Context 系统时，建议按以下顺序决策：

1. **确定 source of truth 的形态**：消息日志？文件系统？数据库？这决定了上下文的边界。
2. **确定装配模型**：编译式（适合长期 Agent）还是切片式（适合任务型 Agent）？
3. **定义优先级层级**：哪些内容是必须保留的，哪些可以被压缩，哪些可以直接丢弃。
4. **选择压缩策略**：truncation（零成本）、summarization（语义保留好）、hybrid（工具输出 truncate + 对话 summarize）。
5. **设计触发机制**：阈值触发？手动触发？周期触发？还是混合？
6. **设计 recall 路径**：被压缩的内容如何找回？关键词搜索？向量检索？还是子 Agent 分析？

### 可观察的不变量

一个健康的 Context 系统应该满足：

- **System prompt 在任何压缩后都不变**。如果 system 被压缩改了，Agent 的行为就漂移了。
- **压缩次数与任务长度呈对数关系**，而不是线性——否则就是在反复压缩同样的内容。
- **Recall 命中率可测**。不能说"有记忆"但从不被调用。

### 从最小实现到生产实现的路径

```text
阶段 1: 线性消息列表 + 简单 truncation
  ↓  增加优先级分层
阶段 2: system/project/history 分层 + 末尾截断
  ↓  增加语义压缩
阶段 3: 自动 summarization + summary 指针
  ↓  外置记忆
阶段 4: 独立 memory 存储 + recall 机制
  ↓  编译式架构
阶段 5: ContextCompiler + MemFS + dreaming/reflection
```

## 8. 实践练习

### 练习：实现一个带优先级的 ContextCompiler（30-45 分钟）

**目标**：用 TypeScript 写一个 `ContextCompiler` 类，支持按优先级和 token budget 装配上下文，触发压缩并保留恢复指针。

**要求**：

1. 定义四类来源，优先级从高到低：
   - `system`（必须放入，超预算则报错）
   - `memory`（可选，按重要性排序）
   - `recentHistory`（最近的对话，从新到旧）
   - `oldHistory`（较早的对话，从新到旧）
2. 实现 `compile(budget): { messages: Message[], remainingBudget: number }`，按优先级装配直到用完预算。
3. 实现 `triggerCompaction(): CompactionArtifact`，把 `oldHistory` 的前半段替换为摘要（用一个简单的"模拟摘要"函数代替真实 LLM 调用）。
4. artifact 中包含：`summary`、`replacedIds`、`compactedAt`。
5. 验证：压缩后重新 compile，working set 的 token 用量显著下降，但 system 和 recentHistory 不受影响。

**验收标准**：

- system 内容超预算时抛出明确错误，而不是静默截断。
- 同一份 source of truth，多次 compile 的结果是确定的（没有随机性）。
- 压缩后，可以通过 artifact 的 `replacedIds` 找到被替换的原始消息。

## 9. 掌握检查

### 自测问题

1. **为什么说 "context window 是编译产物，不是数据库"？** 这两种视角在设计上会导致什么不同的架构选择？
2. **Letta Code 的 MemFS 和 Codex 的 message history，作为 source of truth 有什么本质区别？** 各自适合什么场景？
3. **压缩（compaction）和截断（truncation）的核心区别是什么？** 为什么不能只用截断？
4. **"压缩本身也是成本"是什么意思？** 你会如何衡量一次压缩是否值得？
5. **什么是恢复指针（recovery pointer）？** 如果压缩后不留恢复指针，会发生什么问题？

### 生产落地检查清单

- [ ] **明确的优先级分层**：哪些内容永不压缩，哪些可以摘要，哪些可以直接丢弃，有明确规则。
- [ ] **压缩触发可观测**：每次压缩的触发原因、前后 token 数、耗时、压缩策略都有日志。
- [ ] **压缩失败有兜底**：模型压缩失败不会导致 Agent 卡死，有 truncation 降级路径。
- [ ] **Source of Truth 可重建**：即使 working set 被破坏，也能从完整历史 + 记忆库重新编译出当前状态。
- [ ] **Recall 路径可用**：被压缩/外置的信息有明确的找回机制，且有命中率监控。
- [ ] **多次压缩有保护**：不会因为反复压缩导致关键信息丢失或任务漂移。
- [ ] **内存与 token 的双预算**：不仅限制 token，也限制存储大小，防止历史无限膨胀。

### 常见误区

1. **误区：窗口越大越好，不需要压缩。**  
   真相：窗口越大，每轮调用成本越高；而且大窗口不代表信息组织得好——垃圾信息放得越多，干扰越大。

2. **误区：向量检索就是长期记忆。**  
   真相：向量检索是 recall 的一种技术手段，不是记忆系统本身。记忆还包括组织、编辑、遗忘、版本控制——这些是向量库不关心的。

3. **误区：压缩摘要越详细越好。**  
   真相：摘要越长，省的 token 越少，而且多次压缩后摘要会变得越来越冗余。摘要的目标是"保留足够的恢复线索"，不是"保留全部细节"。

4. **误区：让 Agent 自己管理记忆就够了。**  
   真相：Agent 可以编辑记忆内容，但记忆的装配顺序、投影规则、预算控制必须由 Harness 强制——否则 Agent 可能意外覆盖关键信息或制造无限膨胀。

5. **误区：ContextCompiler 只要在调用模型前跑一次就行。**  
   真相：工具返回可能一次就吃掉大量 token，需要在每轮的多个时间点检查预算——追加消息后、工具返回后、甚至工具调用前。

## 10. 边界与延伸阅读

### 适用边界

本文讨论的是"对话式 Agent 的上下文管理"，不适用于：

- 纯 RAG 系统（关注点是检索质量，不是对话历史管理）。
- 无状态的单轮工具调用（没有历史累积问题）。
- 流式长文本处理（用 map-reduce 模式，不是 context window）。
