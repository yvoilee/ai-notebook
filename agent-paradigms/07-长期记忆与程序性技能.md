# 07 · 长期记忆与程序性技能

> 核验日期：2026-08-30
> 主项目：Letta Code / TypeScript
> 对照项目：Hermes Agent、OpenClaw、DeerFlow

## 1. 一句话掌握

长期记忆是 Agent 跨会话持久化的事实、经验与身份信息，程序性技能（Skill）是从重复成功轨迹中提炼的可复用操作流程；二者共同解决"上下文窗口装不下、每次对话从零开始"的问题，但必须处理写入策略、召回精度、版本化、遗忘和记忆投毒等工程挑战。

## 2. 为什么需要它

### 问题从何而来

Agent 的上下文窗口有硬上限。一个长期运行的 Coding Agent 可能经历上百次会话：修复过的 bug、项目约定、用户偏好、特定工具的用法细节，不可能全部塞进 system prompt。朴素做法——把所有历史塞进去——会迅速耗尽 token、推高成本，并因中间干扰导致召回质量下降。

更隐蔽的问题是：模型在对话中"学到"的程序性知识（如"部署这个项目要先跑 `make build` 再跑 `scripts/deploy.sh`"）在下一次对话中完全丢失。Agent 不会因为做过十次类似任务而变得更快、更准。

### 朴素实现为何失败

1. **全量记忆不可行**：线性增长的记忆与固定窗口构成根本矛盾，必须有遗忘与压缩机制。
2. **纯向量检索不可靠**：语义相似不等于"当前步骤需要"，缺少 provenance 和置信度会引入幻觉。
3. **无写入策略=污染**：模型可以写记忆但没有审计和批准门，错误事实一旦写入就持续污染后续会话（memory poisoning）。
4. **技能无版本=退化**：技能被反复修改但没有版本号和回滚机制，一次错误编辑可能永久降低能力。

### 相关理论

认知科学中的三类记忆为 Agent 记忆系统提供了概念框架：
- **情景记忆（episodic）**：按时间组织的事件序列，如"上次修这个 bug 用了三步"。
- **语义记忆（semantic）**：事实与概念，如"用户偏好 TypeScript 严格模式"。
- **程序性记忆（procedural）**：可执行的操作流程，即技能（skill）。

**巩固（consolidation）** 是将短期经验转为长期记忆的过程；**召回（retrieval）** 是根据当前线索提取相关记忆；**遗忘（forgetting）** 是主动或被动移除失效记忆。

### 在 Harness/Runtime 中的位置

长期记忆与程序性技能属于 **Harness 层** 的 context / memory 子系统，向下依赖 durable state 做持久化，向上向 ContextCompiler 提供素材。技能还与 tool dispatch 交互——技能可以声明 `allowed-tools` 来限制运行时可用工具集。

### 语言无关伪代码

以下伪代码展示写入、召回和技能提炼三条主路径，覆盖去重、置信度、过期和错误处理。

```
function write_memory(item, policy):
    // 去重：内容相似且置信度≥当前的跳过
    existing = find_similar(item.content, threshold=0.92)
    if existing and existing.confidence >= item.confidence:
        return SKIPPED_DUPLICATE

    // 投毒防护：低置信度或不可验证来源需要审核
    if policy.require_review and item.confidence < 0.8:
        queue_for_review(item)
        return PENDING_REVIEW

    item.created_at = now()
    if policy.default_ttl:
        item.expiry = now() + policy.default_ttl

    store.put(item)
    return WRITTEN

function recall(query, types, top_k):
    // 过滤已过期项
    candidates = store.query(query, types, active_only=true)
    // 按置信度 + 相关性排序
    ranked = sort_by(candidates, score = relevance * confidence)
    return ranked[0:top_k]

function consolidate_skill(trajectories, skill_name):
    // 从多条成功轨迹中提炼可复用流程
    common_steps = extract_shared_patterns(trajectories, min_occurrence=2)
    if len(common_steps) < 3:
        return ERROR_INSUFFICIENT_EXAMPLES

    artifact = SkillArtifact{
        name: skill_name,
        version: bump_version(existing_version(skill_name)),
        body: render_procedure(common_steps),
        provenance: map(trajectories, t => t.id),
        hash: content_hash(body + version)
    }
    skill_store.put(artifact)
    return artifact.version
```

## 4. 关键设计决策

### 决策 1：记忆是 system prompt 冻结块，还是按需召回？

- **冻结块（Hermes 风格）**：会话启动时把全部记忆注入 system prompt，运行中不再改变。优点是模型每轮都可见、无召回遗漏；缺点是记忆容量受 token 限制（Hermes memory 约 800 token），必须手动巩固。
- **按需召回（Letta / DeerFlow 风格）**：记忆外置存储，模型通过 `recall` 工具或 ContextCompiler 按需要取。优点是容量几乎无限；缺点是召回质量取决于检索策略，可能遗漏关键信息。
- **失败模式**：冻结块在信息超出容量后必须靠模型手动合并，易丢失细节；按需召回落入"不知道自己不知道"的盲区。

### 决策 2：谁有权写记忆——模型自动写入，还是人工审批？

- **自动写入**：延迟低，但可能写入错误事实或 prompt injection 内容（memory poisoning）。
- **人工审批（write_approval gate）**：Hermes 和 DeerFlow 都支持。写入先进入 pending 队列，用户 approve 后才生效。安全但有交互延迟。
- **混合策略**：高置信度（如从工具输出直接提取的事实）自动写入，低置信度（模型归纳的结论）待审核。
- **失败模式**：全自动写入在长周期中必然积累噪音；全人工审批让记忆系统形同虚设。

### 决策 3：技能是 Markdown 流程文档，还是可执行代码？

- **Markdown 流程（Hermes / OpenClaw / DeerFlow 的 SKILL.md）**：技能是结构化的自然语言指令，模型阅读后自行执行。优点是易创作、易审计、跨模型可迁移；缺点是执行精度依赖模型能力。
- **代码/脚本技能**：技能包含可直接运行的脚本，模型只负责参数化调用。优点是执行确定性高；缺点是创作成本高、跨环境难迁移。
- **实践收敛**：大多数项目采用 SKILL.md + 可选 `scripts/` 子目录的混合模式。流程用自然语言描述，重复性操作沉淀为脚本。

### 决策 4：技能版本化：内容哈希还是语义版本号？

- **内容哈希（Hermes bundled skills）**：用 hash 追踪技能是否被修改，用于判断是否需要从上游更新。
- **语义版本号（通用做法）**：`major.minor.patch`，明确标识破坏性变更。
- **项目特有**：Hermes 同时维护 hash（用于检测变更）和 `version` 字段（用于展示）；DeerFlow 有 `contracts/skill_review/` 版本化契约。
- **失败模式**：无版本化的技能在反复编辑后可能退化，且无法回滚到已知可用版本。

#### 记忆写入与召回

第一段代码展示 `MemoryStore` 的核心写入去重、置信度门控和按 TTL 过滤的召回逻辑。

```typescript
// 教学等价代码：Letta Code 风格的记忆写入与召回
interface MemoryItem {
  id: string;
  type: "episodic" | "semantic";
  content: string;
  provenance: { source: string; sessionId: string; timestamp: number };
  confidence: number; // 0-1
  expiry?: number;
}

interface SkillArtifact {
  name: string;
  version: string;
  description: string;
  body: string;         // 程序性流程（Markdown）
  allowedTools: string[];
  provenance: string[]; // 来源 trajectory ID
  hash: string;
  createdAt: number;
}

class MemoryStore {
  private items = new Map<string, MemoryItem>();

  write(item: MemoryItem, policy: { autoApprove: boolean; minConfidence: number }) {
    for (const existing of this.items.values()) {
      if (existing.type === item.type && this.similar(existing.content, item.content) > 0.9) {
        return { status: "skipped_duplicate", id: existing.id };
      }
    }
    if (!policy.autoApprove || item.confidence < policy.minConfidence) {
      return { status: "pending_review", id: item.id };
    }
    this.items.set(item.id, item);
    return { status: "written", id: item.id };
  }

  recall(query: string, type?: MemoryItem["type"], topK = 5): MemoryItem[] {
    const now = Date.now();
    return [...this.items.values()]
      .filter(m => !m.expiry || m.expiry > now)
      .filter(m => !type || m.type === type)
      .map(m => ({ m, score: this.relevance(m.content, query) * m.confidence }))
      .sort((a, b) => b.score - a.score)
      .slice(0, topK)
      .map(r => r.m);
  }

  private similar(a: string, b: string): number { /* 简化：实际用 embedding 余弦相似度 */ return 0; }
  private relevance(content: string, query: string): number { /* 简化：实际用检索引擎 */ return 0.5; }
}
```

#### 从轨迹提炼版本化技能

第二段代码展示 `consolidateToSkill`：从多条成功轨迹中提取共同步骤，生成带 provenance 和内容哈希的 `SkillArtifact`。

```typescript
// 教学等价代码：从成功轨迹提炼版本化 SkillArtifact
function consolidateToSkill(trajectories: { id: string; steps: string[] }[], name: string): SkillArtifact | null {
  if (trajectories.length < 2) return null;
  const common = findSharedSteps(trajectories.map(t => t.steps));
  if (common.length < 3) return null;

  const body = `# ${name}\n\n## Procedure\n${common.map((s, i) => `${i + 1}. ${s}`).join("\n")}`;
  return {
    name,
    version: "0.1.0",
    description: `Auto-consolidated from ${trajectories.length} trajectories`,
    body,
    allowedTools: ["bash", "read_file", "write_file"],
    provenance: trajectories.map(t => t.id),
    hash: cryptoHash(body + "0.1.0"),
    createdAt: Date.now(),
  };
}

function findSharedSteps(stepLists: string[][]): string[] {
  if (stepLists.length === 0) return [];
  const counts = new Map<string, number>();
  stepLists.forEach(steps => steps.forEach(s => counts.set(s, (counts.get(s) || 0) + 1)));
  return [...counts.entries()]
    .filter(([, c]) => c >= Math.ceil(stepLists.length / 2))
    .map(([s]) => s);
}

function cryptoHash(s: string): string {
  return require("crypto").createHash("sha256").update(s).digest("hex").slice(0, 16);
}
```

**关注点**：
1. `MemoryItem` 中的 `provenance` 字段记录来源会话和时间戳，支持审计和记忆污染溯源。
2. `confidence` 与写入策略共同构成"软门控"——不是简单的允许/拒绝，而是按置信度分级处理。
3. `consolidateToSkill` 展示了从经验轨迹到程序性技能的提炼路径：需要多条成功轨迹、提取共同步骤、生成版本化 artifact。
4. `expiry` 字段让情景记忆可以自然过期，避免无限积累。

> 源码事实 vs 教学简化：Letta Code 的真实记忆系统建立在 MemFS（Git-backed filesystem）上，记忆块是文件而非内存对象；以上代码将存储层抽象为 `Map`，聚焦写入/召回/巩固的决策逻辑，便于理解核心机制。

### 共同收敛的设计

1. **技能即目录 + SKILL.md**：四个项目都采用了"一个技能一个目录、入口文件为 SKILL.md"的格式，支持附带脚本和引用资源。这一格式正通过 agentskills.io 趋于形成事实标准。
2. **渐进式技能加载**：技能不全量塞进上下文，而是先给索引（name + description），需要时再 view 全文。
3. **写入安全门控**：所有项目都认识到"模型可写持久记忆"是风险面，要么提供 approval gate，要么提供扫描器，要么两者都有。

### 仍有分歧的设计

1. **记忆放置位置**：Hermes 选择"system prompt 冻结块 + 容量限制"，Letta 和 DeerFlow 选择"外置存储 + 按需召回"。前者简单可靠，后者容量大但依赖检索质量。
2. **巩固是否自动**：Letta 有 dreaming/sleeptime 后台巩固；Hermes 是模型手动巩固（写满时 error 提示 consolidate）；DeerFlow 的巩固策略未明确公开。
3. **技能安全审查深度**：DeerFlow 有 SkillScan（确定性）+ LLM review 两层；Hermes 有 security scanner（exfiltration/injection/destructive 检测）；OpenClaw 依赖 skill-creator 的验证流程；Letta 依赖 memory confinement 的沙箱隔离。

### 项目特有但不可盲目迁移的设计

- **Letta 的 MemFS + Git 同步**：把记忆变成可 Git 同步的文件系统，天然版本化和可审计。但这要求 Agent 能理解文件系统操作，对非代码类 Agent 不适用。
- **Hermes 的冻结块 + 手动巩固**：实现极简、可预测性强。但 800 token 的容量上限使其不适合需要大规模事实记忆的场景。
- **DeerFlow 的 per-user 记忆隔离**：面向多用户 SaaS 场景的设计，对单用户个人 Agent 是过度工程。

## 7. 方法论抽象

### 设计原则

1. **写入比读取更重要**：低质量记忆比没有记忆更糟。先把写入策略、去重、置信度和审计做好，再谈召回算法。
2. **provenance 是一等公民**：每条记忆必须可追溯到来源会话、来源工具输出来源。没有 provenance 的记忆无法审计、无法清理。
3. **技能是凝固的成功轨迹**：不要从理论推导技能，要从反复成功的 trajectory 中提炼。低于 2 次成功验证的流程不应晋升为技能。
4. **遗忘是功能不是 bug**：情景记忆必须有 TTL 或衰减机制，否则记忆仓库会变成垃圾场。语义记忆也需要定期 review。

### 决策顺序

落地一个记忆系统时，按以下顺序决策可以避免返工：

1. 先确定**记忆类型**：只需事实记忆（semantic），还是需要程序性技能（procedural），还是需要完整情景回放（episodic）？
2. 再确定**召回模型**：冻结注入（容量小但可靠）还是按需召回（容量大但有盲区）？
3. 然后是**写入策略**：谁能写、写什么、是否需要审批、置信度阈值是多少？
4. 最后才是**存储引擎**：SQLite + FTS5、向量数据库、文件系统 + Git，还是混合方案？

### 可复用数据模型

```
MemoryItem { id, type, content, provenance{source,session,timestamp}, confidence, expiry, tags }
SkillArtifact { name, version, description, body, allowed_tools, provenance[], hash, status }
WritePolicy { auto_approve_types[], min_confidence, require_review_types[], default_ttl }
RecallQuery { query, types[], top_k, min_confidence, include_expired? }
```

### 从最小实现到生产实现的路径

1. **最小实现**：一个 JSON 文件 + 手动编辑的 SKILL.md。能跑通"写入-召回-使用"闭环。
2. **基础版本**：SQLite + FTS5 做全文检索，加入 provenance 和 expiry。技能有 version 字段。
3. **增强版本**：加入 embedding 向量检索 + 混合召回。写入加去重和置信度门控。技能有自动提炼管道。
4. **生产版本**：写入审批流、记忆审计面板、技能版本管理 + 回滚、记忆污染检测、定期巩固（dreaming）。

## 8. 实践练习

### 30–60 分钟练习：为一个简单 Agent 实现带 provenance 的记忆系统

**目标**：用 TypeScript 或 Python 实现一个 `MemoryStore`，支持写入、去重、按置信度召回、TTL 过期，并实现一个从轨迹提炼技能的 `consolidateSkill` 函数。

**步骤**：

1. 定义 `MemoryItem` 接口（含 type、content、provenance、confidence、expiry）和 `SkillArtifact` 接口。
2. 实现 `MemoryStore.write(item, policy)`：做内容去重（可用简单的子串匹配或 Jaccard 相似度代替 embedding），按置信度决定写入或 pending。
3. 实现 `MemoryStore.recall(query, type, topK)`：不过期、按置信度 × 相关性排序。
4. 实现 `consolidateSkill(trajectories, name)`：从至少 2 条成功轨迹中提取共同步骤，生成 v0.1.0 的 SkillArtifact。
5. 编写测试用例：
   - 写入两条相似记忆，验证去重生效。
   - 写入低置信度记忆，验证进入 pending 而非直接写入。
   - 写入带 TTL 的记忆，过期后验证 recall 不返回。
   - 给 3 条有共同步骤的轨迹，验证技能提炼成功且带 provenance。

**验证标准**：所有测试通过；provenance 字段在每条记忆和每个技能中都可追溯。

## 9. 掌握检查

### 自测问题

1. 为什么说"纯向量检索的记忆系统"是不可靠的？provenance 和 confidence 在其中起到什么作用？
2. Hermes 的"system prompt 冻结块"方案与 Letta 的"按需召回"方案各自的失败模式是什么？什么场景下选择前者？
3. 什么是 memory poisoning？列举三种防止记忆投毒的工程手段。
4. 为什么技能提炼至少需要 2 条成功轨迹？只从 1 次成功经验生成技能有什么风险？
5. 解释 consolidation（巩固）和 recall（召回）的区别，以及它们分别在 Agent 的哪一层执行。

### 生产落地检查清单

- [ ] 每条记忆有 provenance（来源会话 + 时间戳 + 原始依据）
- [ ] 写入有去重机制和置信度门控
- [ ] 有 write_approval 或等效安全机制，低置信度写入不直接生效
- [ ] 情景记忆有 TTL 或衰减机制，不会无限增长
- [ ] 技能有版本号和内容哈希，支持回滚
- [ ] 技能提炼有"至少 N 次成功"的门槛
- [ ] 有记忆审计面板，可查看、编辑、删除单条记忆
- [ ] 召回结果按相关性 × 置信度排序，而非纯语义相似度
- [ ] 有定期巩固/清理机制（dreaming 或手动 review）
- [ ] 能回答"这条记忆是哪次会话、因为什么写入的"

### 常见误区

1. **把长上下文当长期记忆**：长上下文窗口解决的是单会话容量问题，不是跨会话持久化问题。混淆二者会导致每次新会话仍然"从零开始"。
2. **追求"完美召回"而全量注入**：全量注入看似不会遗漏，但实际会因中间干扰和 token 浪费而降低整体推理质量。
3. **让模型自由写记忆**：没有审批、没有置信度、没有 provenance 的记忆写入是记忆投毒的温床。
4. **技能越写越多=越聪明**：没有巩固和淘汰机制的技能库会越来越臃肿，检索和选择成本超过收益。
5. **把技能写成工具调用的包装**：如果一个"技能"只是"调用 tool X 传参数 Y"，那它应该是工具的使用说明，不是独立技能。技能的价值在于跨工具的流程编排和错误处理模式。

## 10. 边界与延伸阅读

### 适用边界

- 本篇讨论的是 **Agent Harness 层的长期记忆与程序性技能**，不涵盖模型权重层面的持续学习（continual learning）。
- 重点是**可工程化的记忆系统**，即存储结构、写入策略、召回算法和安全机制，不讨论认知科学层面的记忆理论。
- 技能格式以 agentskills.io 风格的 SKILL.md 为主，这是当前开源生态的事实收敛方向。

### 不适用场景

- 单会话短任务：不需要长期记忆，直接用上下文即可。
- 精确事实检索：应该用结构化数据库或 RAG 系统，而不是 Agent 自写的记忆库。
- 安全等级极高的场景：模型生成的记忆有不可控的污染风险，应限制写入权限或仅写入经过严格验证的事实。
